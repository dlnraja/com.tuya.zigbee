- 20:07 (Paris) — **P3047 publish payload JSON written as ASCII** (owner decision 19:48, follow-up to P3046). V8 keeps a string one byte per char only if every char is at most U+00FF; a single arrow or emoji in app.json makes the whole text two-byte, which is the `JsonParser<unsigned short>` seen in the Bastien OOM. New `scripts/maintenance/ascii-json.cjs` is the last write of `scripts/prepare-publish.js` (after every app.json write, before validation and export): app.json and every JSON file of the temp payload are re-serialised with each non-ASCII char as `\uXXXX`. Each file is checked with isDeepStrictEqual on the parsed values before it is written; if app.json would pass 4 MB, it falls back to escaping only chars above U+00FF. Sources, CI and enrichment scripts keep readable UTF-8. Measured on stable-v5: 71 files; published app.json 2.89 -> 2.96 MB on disk (ascii mode, under 4 MB); its in-memory text at load 5.74 -> 2.96 MB and parse peak 12.0 -> 8.6 MB; all payload JSON parse text 11.76 -> 5.44 MB. Every JSON of the payload parses deep-equal before and after, none keeps a non-ASCII char, and `homey app validate --level publish` passes on the escaped payload. Test `test/critical/p3047-ascii-json-payload.test.js` (6 tests: round trip with emoji, lone surrogate and non-ASCII keys, wide mode, tree pass, 4 MB fallback, heap halved, step order). No guard test needed a change. Shipped on bastien-home first (8de4029cb1), then stable-v5 and master. Limit: if Athom re-serialises app.json on its side, that is outside our control.
