# Lessons of 21/11/2026 (Europe/Paris)

SSOT: `config/architecture/publish-ssot.json` (`lessons20261121`), also on
`config/architecture/dual-app-tracks.json`. These rules apply on master,
stable-v5 and bastien-home.

## 1. AggregateError is a packaged file-count problem

Athom issue [athombv/homey-apps-sdk-issues#488](https://github.com/athombv/homey-apps-sdk-issues/issues/488)
(wouter-athom, 17/11/2026) identified `AggregateError` as a packaged file-count
issue, not a driver-count or manifest-byte cap by itself. A server-side fix was
deployed. A blocking file-count ceiling remains on our side (P3356): **3830
files / 32.7 MB** for the packed archive. #3716 reached Test at 347 drivers /
3739 files; #3717 v9.0.1636 reached Test at 368 drivers / 3253 files, under the
ceiling. See `docs/knowledge/ATHOM_LIMITS.md` and
`config/upload-manifest-ceiling.json`.

## 2. Superseded builds are terminal

When Athom marks a build `superseded` (a newer build replaced it), that build is
final, not busy. Do not wait on it as if it were still processing. Treating
#3715 as busy stalled #3717 for 12 minutes. Wired in
`.github/scripts/athom-publish-policy.js` and `wait-athom-idle.js`.

## 3. P3320 honours `.gitignore`

The shipped-JS Latin-1 / packaged-image gate (P3320) must honour `.gitignore`
(and `.homeyignore`) and must not flag gitignored files such as screenshots as
unreferenced packaged images. See `docs/rules/SHIPPED_JS_LATIN1.md` and
`docs/rules/DEVELOPMENT_RULES.md` section 8.

## 4. A sacred couple is re-included before FATAL

If prepare-publish would drop a sacred couple or a sacred continuation driver,
re-include it and continue. A FATAL is only for a miss that could not be
re-included. Implementation: `reincludeMissingSacredDrivers` in
`scripts/publish-hold-release.js`, called from `scripts/prepare-publish.js`.

## 5. Held-driver graduation must not steal published couples

A held driver may graduate under its own id only when its exact mfr+pid couples
are not already in the published Test baseline (9.0.1574 / later Test). If the
couples already ship on a published host, keep them there and use
`onMapDeviceClass` (or an equivalent runtime path) on that host so paired
devices keep their published driver id but get the right class and capabilities.
Do not move 1574 couples onto the new id. P3085 leftover holds (21/11/2026):
`co_sensor_dcr_co`, `fan_light_tuya_5_levels`, `motion_sensor_excellux_zg104plv`,
`vibration_sensor_excellux_zg103v`.

## 6. Live is automatic after objective gates, for master and stable only

Live is automatic only after objective gates (CI green, validate publish, no
lost IDs or couples versus the previous Live, Test healthy with no new crash
signals, evidence-driven soak — not a fixed 7 days). This applies to master
(`com.dlnraja.tuya.zigbee`) and stable (`com.dlnraja.tuya.zigbee.stable`)
regularly (`.github/workflows/promote-live.yml`).

**Bastien (`com.dlnraja.tuya.zigbee.bastien`) must never go to Live.** It is only
for Bastien's house (Test / local install). The Live path must refuse that app
id. See `docs/rules/LIVE_PROMOTION.md`.

## 7. Bastien learnings flow to master and stable regularly

Fixes, quirks, DPs and learned mappings found on `bastien-home` are ported
additively, anonymized, per exact couple, to master and then to stable-v5. Never
copy App ID or version, never wholesale-sync the other way. Existing free
workflow: `.github/workflows/bastien-promote-upstream.yml` (twice daily +
dispatch), `tools/ci/bastien-promote-upstream.js`. See
`docs/rules/BASTIEN_HOUSE_APP.md`.

## 8. Never amend or force-push a pushed commit

If a commit is on the remote, put the correction in a **new commit on top**.
Never `git commit --amend` of a pushed commit, never `git push --force` (or
`--force-with-lease`) to master, stable-v5 or bastien-home. Amend is allowed
only while the commit is still local and unpushed.
